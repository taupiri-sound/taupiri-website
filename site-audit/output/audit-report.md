## 2. Security

### 2.1 HTTP Security Headers

- [x] 🔴 **No security headers configured** — [src/next.config.ts](next.config.ts) has no `headers()` function. All of the following headers are missing and should be added:
  - `Content-Security-Policy` (CSP) — prevents XSS and data injection attacks
  - `Strict-Transport-Security` (HSTS) — enforces HTTPS; `max-age=31536000; includeSubDomains`
  - `X-Frame-Options: DENY` — prevents clickjacking
  - `X-Content-Type-Options: nosniff` — prevents MIME-type sniffing
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Permissions-Policy: geolocation=(), microphone=(), camera=()`

  Add a `headers()` async function to `next.config.ts` that applies these to all routes (`'/:path*'`). Note: CSP requires careful configuration to avoid breaking Sanity Studio — exempt `/studio/` or use a more permissive CSP for that path

### 2.2 API & Input Validation

- [ ] 🔴 **Weak input sanitisation in contact API** — `sanitizeInput()` only strips `<` and `>` characters. This does not protect against XSS via entity encoding (`&#60;`), `javascript:` protocol URIs, event handler attributes, or HTML injection in email templates. See [src/app/api/contact/route.ts:44-47](src/app/api/contact/route.ts#L44). Replace with a proper schema validation library (e.g., `zod`) for all contact form inputs, with explicit max lengths and format rules
- [ ] 🟠 **`x-forwarded-for` header used for rate limiting without validation** — the current implementation reads the first IP from `x-forwarded-for`, which can be spoofed by attackers to bypass rate limiting (`X-Forwarded-For: 1.2.3.4`). On Vercel, use the `x-real-ip` header or the `waitUntil` + Vercel's built-in rate limiting instead. See [src/app/api/contact/route.ts:76-77](src/app/api/contact/route.ts#L76)
- [ ] 🟠 **In-memory rate limiting** — the rate limit store is a `Map` that resets on every cold start and does not work across serverless function instances. This is acknowledged in the code comments. Replace with a persistent solution (Upstash Redis, Vercel KV, or Cloudflare Workers KV) for reliable rate limiting. See [src/app/api/contact/route.ts:20](src/app/api/contact/route.ts#L20)
- [ ] 🟠 **No CSRF protection on contact form** — the `POST /api/contact` endpoint accepts JSON from any origin. While the Sanity revalidate webhook uses HMAC signature validation (✅), the contact form does not validate request origin. Add `Origin` header checking or an explicit CSRF token for the contact form API
- [ ] 🟠 **Error details leak in contact API response** — the catch block returns `details: errorMessage` which includes internal error message strings in the JSON response body in production. This could expose implementation details. Remove the `details` field from the production error response. See [src/app/api/contact/route.ts:243-249](src/app/api/contact/route.ts#L243)
- [ ] 🟠 **No rate limiting on `/api/revalidate` endpoint** — the webhook endpoint validates its HMAC signature (✅) but has no rate limiting. A high volume of valid or invalid webhook requests could impact performance. Add basic rate limiting or IP allowlisting for the Sanity webhook source IPs. See [src/app/api/revalidate/route.ts](src/app/api/revalidate/route.ts)
- [ ] 🟡 **`dangerouslySetInnerHTML` for JSON-LD with CMS content** — organisation name, description, and other CMS-sourced strings are embedded directly into inline `<script>` tags without escaping `<` characters. A Sanity content editor could inadvertently (or maliciously) inject `</script>` into these fields. Escape `<` as `\u003c` in JSON.stringify output. See [src/lib/structuredData.ts:310-314](src/lib/structuredData.ts#L310) and [src/app/layout.tsx:96-100](src/app/layout.tsx#L96)
- [ ] 🟡 **No CAPTCHA on contact form** — honeypot bot detection is a good first line of defence (✅) but sophisticated bots bypass honeypots. Add reCAPTCHA v3 (invisible) or hCaptcha as a second layer, especially important if spam becomes an issue

### 2.3 Environment & Secrets

- [x] 🟢 Sensitive environment variables (`SANITY_API_READ_TOKEN`, `SANITY_API_WRITE_TOKEN`, `RESEND_API_KEY`, `SANITY_WEBHOOK_SECRET`) are server-only (no `NEXT_PUBLIC_` prefix)

- [ ] 🟡 **Document required environment variables** — there is no `.env.example` file listing all required variables. Add one to help with onboarding and deployment, without including actual values

### 2.4 Dependency Security

- [ ] 🟠 **No `npm audit` in CI pipeline** — run `npm audit --audit-level=high` as part of the build or a scheduled CI job to catch known vulnerabilities in dependencies. Run `npm audit` now to check current state

If it is only needed in the Studio, it should not add to the frontend bundle. Verify usage and move to devDependencies or remove if unused

## 3. Performance

### 3.1 Core Web Vitals & Measurement

- [ ] 🔴 **No Core Web Vitals baseline established** — without analytics or monitoring in place, there is no data on LCP, INP, or CLS scores. Run Google PageSpeed Insights against the staging URL immediately and again post-launch with the production URL. Target: LCP < 2.5s, INP < 200ms, CLS < 0.1
- [ ] 🟠 **Run Lighthouse audit against staging** — use Chrome DevTools Lighthouse (both mobile and desktop) to get an immediate performance score. Check the "Opportunities" and "Diagnostics" sections for actionable findings
- [ ] 🟡 **Set up Vercel Analytics** — Vercel's built-in Real Experience Score (RES) monitoring is free for hobby/pro plans and tracks Core Web Vitals from real users. Enable it in the Vercel dashboard

### 3.2 Images

- [x] 🟢 `UnifiedImage` component centralises image handling — auto-sizes for HiDPI, handles null/undefined, manages priority for above-fold images
- [x] 🟢 `next/image` optimisation enabled — images from `cdn.sanity.io` are transformed via the Next.js image optimisation pipeline
- [x] 🟢 Hero/logo images use `priority` prop to trigger `<link rel="preload">`
- [ ] 🟡 **AVIF format not configured** — `next.config.ts` does not set `images.formats`. Next.js defaults to WebP only. Add `formats: ['image/avif', 'image/webp']` to enable AVIF delivery (30–50% smaller than WebP for most images), with WebP as fallback. See [next.config.ts:5-12](next.config.ts#L5)
- [ ] 🟡 **No `minimumCacheTTL` configured for images** — Next.js defaults to 60 seconds for image cache TTL. Set `minimumCacheTTL: 31536000` (1 year) in `images` config since Sanity CDN images are content-addressed and never change URLs. See [next.config.ts](next.config.ts)
- [ ] 🟡 **Image sizes and device sizes not tuned** — the default `deviceSizes` and `imageSizes` in Next.js may generate unnecessarily large intermediate sizes. Consider specifying explicit arrays tuned to the actual breakpoints used by the site
- [ ] 🟡 **No blur placeholder (LQIP)** — `UnifiedImage` does not use `placeholder="blur"` with a `blurDataURL`. Adding Low Quality Image Placeholders reduces perceived layout shift and improves perceived LCP. Sanity provides built-in LQIP via the image metadata pipeline

### 3.3 JavaScript & Bundle

- [x] 🟢 `removeConsole: true` in production compiler config
- [x] 🟢 `optimizeCss: true` and `cssChunking: 'strict'` enabled
- [ ] 🟠 **No bundle analyser configured** — it is impossible to identify large dependencies or dead code without running a bundle analysis. Add `@next/bundle-analyzer` as a dev dependency and run `ANALYZE=true npm run build` to inspect chunk sizes
- [ ] 🟡 **`styled-components` bundle impact** — `styled-components` is a sizeable runtime CSS-in-JS library. If it is only used in Sanity Studio (which runs separately), it should not be bundled into the frontend. Verify with a bundle analysis and remove from `dependencies` if frontend-unused
- [ ] 🟡 **`critters` package + manual critical CSS** — `critters` is listed in `dependencies` and is designed to automatically inline critical CSS. However, critical CSS is also manually inlined in [src/app/layout.tsx](src/app/layout.tsx#L70-93). Verify whether `critters` is actually active (it integrates with `optimizeCss: true` in Next.js). If both are running, there may be redundant processing. If `critters` is handling critical CSS extraction automatically, the manual duplication in `layout.tsx` may be unnecessary
- [ ] 🟡 **Consider dynamic imports for heavy below-fold components** — components like `AudioSamplePlayer`, gallery components, and the contact form could be lazy-loaded with `next/dynamic` to reduce the initial JS payload for above-fold content

### 3.4 Resource Loading & Caching

- [x] 🟢 `dns-prefetch` and `preconnect` for `cdn.sanity.io`
- [x] 🟢 ISR with tag-based revalidation — pages cache indefinitely until a Sanity webhook triggers targeted revalidation
- [x] 🟢 `next/font` automatically preloads font files with proper cache headers
- [ ] 🟡 **No explicit `Cache-Control` header on sitemap response** — the sitemap uses `export const revalidate = 3600` for ISR, but the `NextResponse` in [src/app/sitemap.xml/route.ts:85-89](src/app/sitemap.xml/route.ts#L85) does not set an explicit `Cache-Control` header. Vercel may override this with `max-age=0`. Add `'Cache-Control': 's-maxage=3600, stale-while-revalidate'` to the response headers
- [ ] 🟡 **No `<link rel="prefetch">` for likely next pages** — add `<link rel="prefetch">` for high-traffic internal pages (e.g., `/blog`, `/studio-and-equipment`) to preload them in the browser's idle time. Next.js does viewport-based prefetching for `<Link>` components (✅) but manual prefetch hints can supplement this for non-link-visible routes
- [ ] 🟢 **Consider adding `next/image` `deviceSizes`** — tune the `deviceSizes` array to match the actual breakpoints in the design system (xs: 500px, md: 768px, lg: 1024px) to avoid generating intermediate sizes that are never served

## 4. Accessibility

### 4.1 Structure & Navigation

- [x] 🟢 Skip link implemented — `SkipLink` component renders `"Skip to main content"` as the first focusable element, visually hidden until focused ([src/components/UI/SkipLink.tsx](src/components/UI/SkipLink.tsx))
- [x] 🟢 Skip link targets `#main-content` which is the `<main>` element id _(confirmed in layout)_
- [x] 🟢 Semantic HTML structure: `<header>`, `<main id="main-content">`, `<footer>` properly used
- [x] 🟢 Heading hierarchy: H1 → H2 → H3 confirmed on homepage (Services, Music, The Studio, About Us, Contact Us as H2s; specific services as H3s)
- [ ] 🟠 **Multiple `<nav>` elements without `aria-label`** — `HorizontalNav` renders a `<nav>` ([src/components/Header/HorizontalNav.tsx:29](src/components/Header/HorizontalNav.tsx#L29)) and the vertical nav also renders navigation, and the footer likely contains another. Screen readers list all navigation landmarks; without labels, users cannot distinguish between them. Add `aria-label="Main navigation"` to `HorizontalNav`, `aria-label="Mobile navigation"` to `VerticalNav`, and `aria-label="Footer navigation"` to the footer's nav
- [ ] 🟠 **Contact form title renders as `<p>` not a heading** — `{title && <p className='text-h5 font-bold mb-2'>{title}</p>}` ([src/components/\_blocks/ContactForm.tsx:114](src/components/_blocks/ContactForm.tsx#L114)) uses heading styling but a paragraph element. Screen reader users navigating by headings will not find the form title. Change to `<h2>` (or appropriate heading level based on page context)
- [ ] 🟠 **No `aria-live` region for contact form status** — when the form submits successfully or errors, the success/error content appears via React state changes ([src/components/\_blocks/ContactForm.tsx:250-255](src/components/_blocks/ContactForm.tsx#L250)). Screen readers are not notified of this change. Wrap the status region in `<div role="status" aria-live="polite">` so assistive technologies announce the result
- [ ] 🟠 **Error messages not linked to form fields via `aria-describedby`** — the form uses `aria-invalid` (✅) but the error message paragraphs are not linked to their inputs. Screen readers may not associate the error text with the relevant field. Add `aria-describedby="name-error"` to each input and `id="name-error"` to the corresponding error paragraph. See [src/components/\_blocks/ContactForm.tsx:138-157](src/components/_blocks/ContactForm.tsx#L138)

### 4.2 Interactive Components

- [x] 🟢 Menu button has `aria-label`, `aria-expanded`, and `aria-controls` ([src/components/Header/MenuButton.tsx](src/components/Header/MenuButton.tsx))
- [x] 🟢 Escape key closes the navigation menu ([src/components/Header/Header.tsx:68-85](src/components/Header/Header.tsx#L68))
- [x] 🟢 Audio player play/pause button has `aria-label` (dynamic: "Play" / "Pause") ([src/components/AudioSamplePlayer/SingleTrackPlayer.tsx:75](src/components/AudioSamplePlayer/SingleTrackPlayer.tsx#L75))
- [x] 🟢 Timeline range input has `aria-label="Audio timeline"` ([src/components/AudioSamplePlayer/TimelineBar.tsx:28](src/components/AudioSamplePlayer/TimelineBar.tsx#L28))
- [x] 🟢 Volume control range input has `aria-label="Volume"` and mute button has dynamic `aria-label` ([src/components/AudioSamplePlayer/VolumeControl.tsx:23](src/components/AudioSamplePlayer/VolumeControl.tsx#L23))
- [x] 🟢 Modal component has focus trap, Escape key support, and proper ARIA attributes
- [ ] 🟡 **Audio player has no `aria-live` region for current track** — when a track changes in `MultiTrackPlayer`, there is no announcement to screen readers. Add an `aria-live="polite"` region that announces the current track name and artist when the active track changes
- [ ] 🟡 **Audio player wrapper has no `role="region"` or landmark** — the audio player container has no ARIA landmark, making it difficult for screen reader users to navigate to it. Add `role="region" aria-label="Audio player"` to the outermost container
- [ ] 🟡 **Timeline range input thumb not keyboard-visible** — the timeline thumb indicator (`<div>`) is `opacity-0` until hover ([src/components/AudioSamplePlayer/TimelineBar.tsx:31](src/components/AudioSamplePlayer/TimelineBar.tsx#L31)). The underlying `<input type="range">` is keyboard-accessible (✅) but the visual thumb does not appear on focus. Add a `:focus-within` variant to show the thumb when the range input is focused
- [ ] 🟡 **`required` attribute missing on required form fields** — form fields validated as required by `react-hook-form` should also have the HTML `required` attribute so browsers and screen readers natively communicate the requirement. `aria-required="true"` is the ARIA equivalent. See [src/components/\_blocks/ContactForm.tsx:139-157](src/components/_blocks/ContactForm.tsx#L139)
- [ ] 🟡 **Contact form submit button loading state not announced** — when the button text changes from "Send Message" to "Sending...", screen readers are not notified. Add `aria-busy="true"` to the form element during submission

### 4.3 Visual & Motion

- [ ] 🔴 **No `prefers-reduced-motion` support** — no media query for `prefers-reduced-motion` exists anywhere in the codebase (confirmed: zero matches in `src/`). This affects scroll animations, header fade-in, CSS transitions, and any JavaScript-driven animations. Users who have enabled reduced motion in their OS settings receive no accommodation. Add to `globals.css`:
  ```css
  @media (prefers-reduced-motion: reduce) {
    *, *::before, *::after {
      animation-duration: 0.01ms !important;
      animation-iteration-count: 1 !important;
      transition-duration: 0.01ms !important;
    }
    html {
      scroll-behavior: auto;
    }
  }
  ```
  Additionally, the header scroll opacity effect in [src/components/Header/Header.tsx:48-66](src/components/Header/Header.tsx#L48) and any JavaScript animations should check `window.matchMedia('(prefers-reduced-motion: reduce)').matches`
- [ ] 🟡 **Colour contrast not verified** — brand colours `#900000` (primary red) and `#b8956a` (subtle gold) have not been tested for WCAG AA compliance (4.5:1 for normal text, 3:1 for large text) against the background `#fffbe8` (brand white). The gold (`#b8956a`) in particular is at high risk of failing. Test all colour combinations at https://webaim.org/resources/contrastchecker/
- [ ] 🟡 **Focus ring consistency** — the skip link has a custom focus ring (`focus:ring-brand-secondary`). Audit all interactive elements to ensure they all have visible, consistent focus indicators that meet WCAG 2.1 success criterion 2.4.11 (minimum focus appearance). Tailwind's default `outline-none` on some elements may remove focus visibility
- [ ] 🟢 **No dark mode consideration** — the site uses fixed light brand colours with no `prefers-color-scheme: dark` support. This is a low priority for now but worth planning for if the design system evolves

### 4.4 Screen Reader & Keyboard

- [ ] 🟡 **Screen reader testing not yet done** — test the full user journey (navigate to site → read content → use audio player → submit contact form → receive confirmation) with VoiceOver (macOS/iOS) and NVDA (Windows). Pay particular attention to the audio player track list, form validation messages, and the navigation menu
- [ ] 🟡 **Keyboard-only navigation not fully tested** — tab through the entire site using only a keyboard to verify: all interactive elements are reachable, focus order is logical, no keyboard traps exist outside modals, and all custom components (audio player, navigation) are fully operable
- [ ] 🟡 **`autocomplete` attributes missing on form fields** — the contact form inputs for name, email, phone, and message should have appropriate `autocomplete` values (`autocomplete="name"`, `autocomplete="email"`, `autocomplete="tel"`, `autocomplete="off"` for message). This aids users who rely on autofill and is required for WCAG 1.3.5 (Identify Input Purpose). See [src/components/\_blocks/ContactForm.tsx:139-226](src/components/_blocks/ContactForm.tsx#L139)
- [ ] 🟢 **Decorative images should have `alt=""`** — review all images used purely for decoration (backgrounds, dividers, textures). These should have an empty `alt=""` attribute so screen readers skip them. The `UnifiedImage` component should make this easy to audit
